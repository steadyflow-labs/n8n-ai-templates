The one value it got wrong

On document 18, a photocopy with a RECEIVED stamp across line 2, the quantity under the stamp is 30. The reader recorded 36. It also said it couldn't be sure ("could be 38 or 30"), so the order went to a person instead of into the order system. That is the behaviour we want: when ink covers a number, a person should look at it.

What the first run got wrong, and what we changed

We ran the set twice on the same day. The first run scored 493 of 495 fields and 11 of 12 problems, with 2 false alarms. Three things were wrong, and all three were in our checking code or instructions, not in the reading:

  1. A bad "closest match". For an item the supplier doesn't sell at all (ZX-9), the check suggested an unrelated product as the closest match. An empty field in the item list was being counted as a near match. Fixed: only real item codes are compared.
  2. Units written as words. An order typed in an email said "/pad"; the catalog says PD. The check treated them as different units. Fixed: common unit words (each, box, case, pack, pad, set, roll, can) now match their codes.
  3. Too many "unclear" notes. The reader noted that a page was upside down, or that a PO said "exemption on file" without a number. Those notes sent clean orders to review. Fixed: it now notes only values it recorded but couldn't read.

Fixing problems found by a test and then re-running the same test flatters the second score. So treat 494/495 as the result on documents we've seen, and judge us on your own POs: that's what the $79 pilot is for. The first run's full report is kept below.

                          How the test works

                          • Same code as a client install. The request to the model, the checks and the CSV output are loaded unchanged from our published n8n workflow. Model: Claude Sonnet 5.5 through Anthropic's API.
                          • Answer key written first. Each document was generated from a written spec, so the correct PO number, date, customer, ship-to, terms, tax-exempt number and every line (item, quantity, unit, price) are known before the run.
                          • 495 fields across 18 orders, plus 2 documents that must be skipped because they are not orders.
                          • 12 planted problems: mistyped and unknown item numbers, a line with no item number, case/each mix-ups, prices above and below list, a district missing from the customer list, a handwritten quantity change, and the two non-orders.
                          • Cost: about 81,000 input and 16,000 output tokens for all 20 documents, a few cents per document.

                          Reports: run 1 · run 2. Next: a fresh set we haven't seen, so the score isn't measured on documents we've already fixed against.
